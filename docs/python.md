# OpenDleto for Python

The Python package is a native NumPy/SciPy implementation of selected OpenDleto operations. It does not require a Julia installation or runtime. Its Julia reference is beta commit `4635b39bf4837bb99919ff887e467f2bc329c528`; the Python API and numerical behavior are not a complete port.

## Installation

Python 3.10 or newer is required. From a clone of the `beta-python` branch:

```sh
python -m pip install ./python
```

Once the branch is available on GitHub, install directly from its subdirectory:

```sh
python -m pip install 'opendleto @ git+https://github.com/thetensor-space/OpenDleto.git@beta-python#subdirectory=python'
```

For optional PyTorch support:

```sh
python -m pip install 'opendleto[torch] @ git+https://github.com/thetensor-space/OpenDleto.git@beta-python#subdirectory=python'
```

The branch URL follows its latest commit; pin a commit instead of `beta-python` for a reproducible installation. NumPy and SciPy are installed as dependencies.

## Basic use

```python
import numpy as np
from opendleto import derivations, nondeg

T = np.random.default_rng(0).normal(size=(3, 3, 3))
reduction = nondeg(T)
print(reduction.ranks, np.linalg.norm(T - reduction.reconstruct()))
result = derivations(T)
print(result.nontrivial_nullity_estimate, result.exact, result.residuals)
```

Inputs may be native NumPy arrays or wrapped in `TensorElement` with `tensor(T)`. The wrapper holds a native array or PyTorch tensor in `.data`; it does not depend on Julia ITensors.

`nondeg` returns a core and orthonormal bases for the selected zero-based axes. Its default truncated HOSVD keeps singular values strictly greater than `tol` times the largest singular value of each original mode unfolding. `mode="full"` retains complete bases; a zero unfolding has rank zero in truncated mode.

`derivations` and `derivation_nullity` return a `DerivationResult`. For sufficiently small maps, a complete dense SVD gives the nullity at the requested relative tolerance (`exact=True`). For larger maps, a matrix-free iterative solve examines only part of the spectrum (`exact=False`); `nullity_lower_bound` and `nontrivial_nullity_estimate` are partial results, and convergence and residuals should be checked. The iterative threshold uses its own scale estimate, so it is not identical to the dense threshold. `total_nullity` is `None` for a partial solve. The returned nontrivial count excludes the permitted scalar gauge: combinations of scalar identity operators that satisfy the chisel equations. `max_vectors` limits returned vectors, even when the dense count is larger.

## Feature coverage

| Feature | Python coverage |
| --- | --- |
| Chisels and transverse operators | Universal, Tucker, adjoint and centroid chisels; independent universal, diagonal, symmetric, antisymmetric, scalar and empty operator spaces. Signed coupled transverse symmetries are available through `TransverseOpsSymmetries`; engagement reduction of coupled spaces is not exposed. |
| Derivation maps | `DerivationMap` provides forward, adjoint and normal actions; `sylvesterLM` exposes SciPy linear operators. NumPy and CPU PyTorch are supported. PyTorch GPU forward is available, but GPU adjoint and solver are unsupported. |
| Derivations | Dense SVD and partial matrix-free nullspace diagnostics through `derivations` and `derivation_nullity`; not all Julia solvers are ported. |
| Nondegenerate reduction | NumPy `nondeg` supplies full and truncated HOSVD. Its relative cutoff and zero-tensor handling differ from the Julia reference's absolute cutoff and zero fallback. |
| Stratification | NumPy `stratify` constructs frames from a returned derivation and reports a support mask when safely diagonalizable; otherwise it returns Schur frames without a mask. This is a subset of Julia functionality. |
| Other Julia features | Densors, autodiff and other unlisted Julia functionality are not supported. |

PyTorch support is optional and does not provide an autodiff API; use explicit conversions when moving between NumPy and PyTorch or between CPU and GPU.

## Reproducible checks and performance

Run the Python tests with `python -m pytest python/tests` after installing the `dev` extra, or with the standard library runner `PYTHONPATH=python/src python -m unittest discover -s python/tests -p 'test_*.py'`. The tests include a stored Julia fixture generated by `python/examples/generate_julia_fixture.jl`; ordinary Python tests read the fixture without invoking Julia. The [recovery notebook](../python/examples/recovery.ipynb) demonstrates an invertible coordinate change, nontrivial derivations, a structural support mask, reconstruction error and a generic random control.

The [benchmark script](../python/examples/benchmark.py) measures forward and adjoint map applications without constructing the dense map. On the development machine, NumPy float64 CPU, two repetitions after one warmup, the minimum observed times were:

| Tensor | Forward | Adjoint |
| --- | ---: | ---: |
| 32³ | 0.00023 s | 0.00011 s |
| 64³ | 0.00265 s | 0.00129 s |
| 100³ | 0.00407 s | 0.00230 s |
| 128³ | 0.03665 s | 0.04571 s |

These are operation timings, not end-to-end derivation solves. The script also reports the process peak resident set size in the host operating system's native units. Its timings vary with hardware and memory layout; no Julia speed comparison was measured.

`stratify` reports operator entries, frame entries, support-description entries, permitted coefficient count and an estimated total entry count. These are storage estimates, not a compression claim. The algebraic support mask is derived from eigenvalue grading; the energy and reconstruction error are separate numerical diagnostics. Defective or ill-conditioned generators yield Schur frames without a coefficientwise mask.

## Julia to Python API map

| Julia reference | Python counterpart | Scope |
| --- | --- | --- |
| `UniversalChisel`, `TuckerChisel`, `AdjointChisel`, `CentroidChisel` | Same names | Zero-based Python axis arguments for `AdjointChisel`. |
| `UniversalOp`, `DiagonalOp`, `SymmetricOp`, `AntiSymmetricOp`, `ScalarOp`, `EmptyOp` | Same names | Native NumPy matrix coordinate bases. |
| `IndTransverseOps`, `TransverseOpsSymmetries` | `TransverseOps`, `TransverseOpsSymmetries` | Independent and signed shared/transpose relationships; no engaged-axis reduction for coupled spaces. |
| `sylvesterLM` | `sylvesterLM`, `DerivationMap` | Matrix-free forward, adjoint and normal maps. |
| `der`, `derTrOpsReduced` | `derivations`, `derivation_nullity` | Dense exact or matrix-free partial solves, with scalar gauge diagnostics. |
| `nondeg` | `nondeg` | Full or truncated HOSVD with a relative cutoff. |
| `stratify` | `stratify` | One discovered generator; diagonal frames or conservative Schur fallback. |

## Apple silicon GPU

Install the optional backend in a project environment with `python -m pip install -e './python[torch,dev]'`. On Apple silicon, select a PyTorch tensor on the `mps` device and verify `torch.backends.mps.is_available()`. The derivation map's forward action accepts MPS tensors and retains the output on MPS. For example:

```python
import torch
from opendleto import DerivationMap

assert torch.backends.mps.is_available()
T = torch.randn((3, 4, 5), device="mps", dtype=torch.float32)
D = DerivationMap(T)
x = torch.randn(D.shape[1]).numpy()
y = D.forward(x)
print(y.device)
```

The MPS backend does not support `float64` or `complex128`; use the NumPy CPU backend for numerically sensitive calculations requiring those dtypes. The current Python port supports MPS forward contractions, while its adjoint and derivation solver require CPU. GPU availability checks can return false inside a process sandbox even when the host GPU works; the development Mac's MPS check and forward test passed outside the sandbox.

The [minimal Python–Julia and CPU–MPS comparison](../bench/python_vs_julia/README.md) uses identical saved tensor values and operator coordinates. It also verifies the Julia `sylvesterLM` convention that the transpose of each coordinate matrix acts on its tensor mode. On the measured Apple M4 Max, MPS forward contractions become faster than NumPy CPU at 64³ in `float32`, while smaller cases favor CPU. This is a map-operation comparison, not an end-to-end GPU derivation solve.
