# Julia Metal and Python MPS on video-sized tensors

We tested two synthetic `Float32` tensors representing **640 × 480 pixels at
30 frames per second for 10 seconds**: one channel with shape `640 × 480 × 300`,
and RGB with shape `640 × 480 × 3 × 300`. The data are deterministic random
values. Each timed call applies the universal-chisel derivation map to the
**whole tensor**. This is a tensor operation, not video decoding, encoding, or
a frame-by-frame filter.

The one-channel input has 92,160,000 elements (0.34 GiB); RGB has 276,480,000
elements (1.03 GiB). The operator coordinate vectors have 730,000 and 730,009
elements respectively. Julia Metal and Python PyTorch MPS read identical binary
inputs for each case. Both return the full result to the host inside the timed
call. Map construction and the initial tensor upload are excluded. Each process
performs five warmup calls followed by 11 timed calls; the median is reported
in **seconds**. GPU synchronization is included.

As in the larger cubic sweep, CPU timing is omitted. **Both runs were
configured with 12 host threads**: `JULIA_NUM_THREADS=12` and
`torch.set_num_threads(12)`. These settings do not control or measure GPU
device workers. The run used an Apple M4 Max with 64 GiB unified memory,
macOS 27.2.1, Julia 1.12.3 with Metal.jl 1.11.1 in a temporary environment,
and Python with PyTorch 2.15.0.

## Results

![Two panels compare whole-tensor forward-map time and clip-equivalent frames per second on one-channel and RGB 640 × 480, 300-frame tensors. Both backends use 12 configured host threads. The one-channel medians are 0.0573 seconds or 5,233 fps for Julia Metal and 0.0544 seconds or 5,516 fps for Python MPS. The RGB medians are 0.2515 seconds or 1,193 fps for Julia and 0.2171 seconds or 1,382 fps for Python. The panels use separate zoomed time axes; every call is in the linked CSV.](video-2026-11-18.png)

| Tensor | Julia Metal | Python MPS | Julia clip-equivalent fps | Python clip-equivalent fps |
| --- | ---: | ---: | ---: | ---: |
| One channel · `640 × 480 × 300` | 0.0573 s | 0.0544 s | 5,233 | 5,516 |
| RGB · `640 × 480 × 3 × 300` | 0.2515 s | 0.2171 s | 1,193 | 1,382 |

The fps column is `300 frames ÷ median seconds per whole-tensor call`. For one
channel, the medians differ by 0.0029 seconds and their middle-half ranges
overlap (Julia 0.0542–0.0626 s; Python 0.0485–0.0601 s). This run does not
establish a meaningful speed advantage for either implementation. On RGB,
Python MPS measured about **1.16× faster** for this host-facing forward call;
the middle-half ranges were 0.2509–0.2584 s for Julia and 0.2127–0.2193 s
for Python.

**Streaming interpretation:** the fps values are *batch-equivalent throughput*:
300 frames divided by one call on the entire 300-frame tensor. For a
nonoverlapping 10-second chunk, one forward-map call takes roughly 0.22–0.25 s,
so about 40–46 such calls fit within 10 seconds if the map and tensor are
already resident. The first whole-window result still cannot arrive before
the 10-second window closes; latency is at least about 10.22–10.25 seconds
from the first frame, before ingestion and solve overhead.

For an **overlapping 10-second window updated on every incoming frame**,
recomputing the entire forward map would require 30 calls per second. The
measured RGB rates are only about 4.0 Julia or 4.6 Python calls per second.
That pattern would need an incremental algorithm or a shorter window. A full
stratification solve may also require many map applications, plus map updates
and uploads. Those costs were not timed. The current result does not establish
that full live stratification keeps up with a 30 fps stream.

The graph zooms both time axes to show the typical calls. One Julia
one-channel call took 0.199 seconds; two Julia RGB calls took 0.334 and 0.343
seconds; one Python RGB call took 0.157 seconds. [All 44 timed calls](video-results-2026-11-18.csv),
including these outliers, are retained. The median limits their influence.

The two GPU implementations agreed on 16 sampled output elements to a relative
norm difference below `1.4e-8` in each case. Their reported full-output norms
differed by `1.7e-5` relative for one channel and `1.0e-4` for RGB. Sampling
and norms do not prove full elementwise parity.

## Reproduce

Run from the repository root on a Mac with GPU access, the project-local Python
environment, and a Julia environment containing this checkout and Metal.jl
1.11.1. The commands print warmup and call progress to per-case logs. The
plotting Python environment needs NumPy and Matplotlib.

```sh
python/.venv/bin/python bench/python_vs_julia/video_inputs.py /tmp/opendleto-video-mono --shape 640 480 300
JULIA_NUM_THREADS=12 julia --compiled-modules=existing --project=/tmp/dleto-metal-bench bench/python_vs_julia/video_julia.jl /tmp/opendleto-video-mono metal 640 480 300 5 11 | tee /tmp/opendleto-video-mono/julia-metal-12t-5x11.log
python/.venv/bin/python -u bench/python_vs_julia/video_python.py /tmp/opendleto-video-mono --shape 640 480 300 --backend mps --host-threads 12 --warmups 5 --repeats 11 | tee /tmp/opendleto-video-mono/python-mps-12t-5x11.log

python/.venv/bin/python bench/python_vs_julia/video_inputs.py /tmp/opendleto-video-rgb --shape 640 480 3 300
JULIA_NUM_THREADS=12 julia --compiled-modules=existing --project=/tmp/dleto-metal-bench bench/python_vs_julia/video_julia.jl /tmp/opendleto-video-rgb metal 640 480 3 300 5 11 | tee /tmp/opendleto-video-rgb/julia-metal-12t-5x11.log
python/.venv/bin/python -u bench/python_vs_julia/video_python.py /tmp/opendleto-video-rgb --shape 640 480 3 300 --backend mps --host-threads 12 --warmups 5 --repeats 11 | tee /tmp/opendleto-video-rgb/python-mps-12t-5x11.log

MPLCONFIGDIR=/tmp/opendleto-mpl python3 bench/python_vs_julia/plot_video.py /tmp/opendleto-video-mono /tmp/opendleto-video-rgb
```

The [cubic Apple comparison](APPLE-ACCELERATE-2026-11-18.md) provides context
through `512³`.
